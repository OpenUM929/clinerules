# 22. 문서 넘버링·명명 표준

> 채번 규칙이 없으면 서로 다른 세션이 같은 번호를 취한다. 실제로 번호 중복이 2쌍 발생했다.

---

## NUM-1. 파일명 형식

```
NN-<slug>.md
```

| 요소 | 규칙 |
|------|------|
| `NN` | 2자리 숫자, 0 패딩 |
| 구분자 | **하이픈 `-` 하나만**. 점(`.`)·언더스코어(`_`) 금지 |
| `<slug>` | 소문자 영문·숫자·하이픈, 최대 30자. 한글 금지 |

## NUM-2. 폴더명 형식

| 대상 | 규칙 |
|------|------|
| 나침반 분리 폴더 | 나침반 파일명에서 `.md` 를 뺀 것과 **정확히 동일** (`03-plan-mode.md` → `03-plan-mode/`) |
| 주제 폴더 | 소문자 케밥 (`development/`, `operator-manual/`) |
| 프로젝트 폴더 | `projects/<project_id>` → [`20-repo-layout.md`](20-repo-layout.md) N-PRJ |

## NUM-3. 번호 필수 구역 / 선택 구역

| 구역 | 번호 | 근거 |
|------|------|------|
| `common/core/**` (하위 분리 폴더 포함) | **필수** | 읽는 순서·우선순위가 의미를 가진다 |
| `common/{development,ui,verification,operator-manual}/**` | 선택 | 사전(dictionary)형 폴더. 알파벳 정렬로 충분하다. 번호를 쓰면 NUM-1 형식을 지킨다 |
| `projects/**` | 선택 | 동일 |

무번호가 항상 허용되는 파일: `README.md`, `CLAUDE.md`, 전부 대문자인 메타 문서(`NUMBERS.md`, `PROJECTS-REGISTRY.md`).

## NUM-4. 번호 대역

| 대역 | 용도 |
|------|------|
| `00` | 그 폴더의 나침반 (폴더당 1개) |
| `01`–`09` | 불변 규율 — 모든 작업의 전제. 신규 추가는 사용자 승인 필수 |
| `10`–`29` | 절차·산출물 규칙. 통상 신규는 여기 |
| `30`–`89` | 예비 — `10`–`29` 가 차면 여기를 이어 쓴다(`30` 부터 순차) |
| `90`–`99` | 폐기 예정. 상단에 `> ⚠️ DEPRECATED — 대체: <경로>` 명시 |

## NUM-5. 신규 채번 절차

1. [`NUMBERS.md`](../../NUMBERS.md) 를 **Read** 한다.
2. 대상 폴더·대역을 NUM-4 로 결정한다.
3. 그 대역에서 **대장에 기록된 최대 번호 + 1** 을 취한다. 파일 목록이 아니라 **대장**이 근거다(삭제된 번호도 대장에 남아 재사용을 막는다).
4. **대장에 행을 먼저 추가**한다(번호 선점).
5. 파일을 생성한다.
6. 나침반의 라우팅 표에 링크를 추가한다.

> 4번이 핵심이다. 파일부터 만들면 번호 충돌이 재발한다.

## NUM-6. 기존 문서 개정 시

| 상황 | 번호 |
|------|------|
| 내용 보완·수정 | 유지 |
| 문서 분리(나침반화) | 유지. 하위 폴더는 같은 번호·같은 slug |
| 주제 자체가 바뀜 | 새 번호로 신규 생성 + 구 문서를 `90` 대로 이동 후 DEPRECATED |
| 폐기 | 파일 삭제, **번호는 결번으로 영구 보존**(대장에 `삭제` 기록) |

## NUM-7. 번호 중복 해소

**나중에 추가된 쪽**(git `--diff-filter=A` 최초 추가 커밋 기준)이 새 번호로 이동한다. 먼저 있던 문서의 번호를 지켜야 기존 링크와 기억이 유지된다.

## NUM-8. 문서 종류별 명명 체계

지침 문서와 **다른 체계**를 쓰는 문서들이다. 파일명만 보고 종류를 구분할 수 있어야 하므로 통일하지 않는다.

| 문서 종류 | 형식 | 정본 규칙 |
|-----------|------|-----------|
| 지침 문서 | `NN-<slug>.md` | 본 문서 |
| 계획서 | `DD_NN_<slug>.md` (폴더명과 동일) | [`00-core/03-plan-mode.md`](00-core/03-plan-mode.md) |
| CR 보고서 | `REQ-YYMM-NNN[-r].md` | [`06-git-rules.md`](06-git-rules.md) |
| 운영자 메뉴얼 | `NN-<menu>[.tabN].md` | [`../operator-manual/DEVELOPMENT/01-structure.md`](../operator-manual/DEVELOPMENT/01-structure.md) |
| 메타 문서 | `UPPERCASE.md` | 본 문서 NUM-3 |
| 보고서·산출물 | `<제목>_YYMMDD[-NN].md` | 본 문서 **NUM-9** |

## NUM-9. 개정 판번호 — 오늘 몇 번째 고친 문서인지 문서가 스스로 밝힌다

> 고쳤는데 문서에는 과거 날짜만 남아 있으면, 읽는 사람도 다음 세션의 나도 **어느 것이 최신인지 알 수 없다.** 파일 수정시각은 근거가 되지 못한다(복사·이동으로 바뀐다).

**RV-1. 파일명의 날짜는 「최초 발행일」이며 개정해도 바꾸지 않는다.** 다른 문서가 그 이름으로 이 문서를 가리키고 있기 때문이다. 이름을 바꾸려면 참조 전량을 함께 고쳐야 하므로, 참조가 2곳 이상이면 **바꾸지 않는다.**

**RV-2. 개정 회차는 본문 머리말 첫 줄에 `rev-YYMMDD-NN` 으로 적는다** — `YYMMDD` 는 **개정한 날**, `NN` 은 **그날의 몇 번째 개정인지**(01부터). 예: `> 최초 보고일 2026-07-28 · 최종 개정 2026-08-06 (당일 제2차) — rev-260806-02`.

**RV-3. 판마다 파일을 새로 내는 산출물(원페이퍼·요약본 등)은 파일명 자체에 `-NN` 을 붙인다** — `원페이퍼_1장_260806-05.md`. 이때 **구판 전부에 폐기 배너**를 붙이고 정본 파일명을 지목한다. 배너 없이 여러 판이 병존하면 어느 것이 정본인지 파일명만으로는 판별되지 않는다.

**RV-4. 무엇이 바뀌었는지는 문서 안 「개정 이력」 절에 한 행씩 남긴다.** 머리말은 **언제·몇 번째**만, 이력 절은 **무엇을·왜**. 본문 곳곳에 `(2026-08-06 신설)` 을 흩뿌리는 것으로 대신하지 않는다.

**RV-5. 개정 시 상호 참조를 함께 고친다.** 정본이 바뀌었는데 다른 문서가 구판을 「요약본」·「상세 근거」로 가리키고 있으면 그 자체가 결함이다. 참조는 `grep` 으로 전수 확인한다.

| 위반 징후 | 실제 사례 |
|---|---|
| 오늘 고쳤는데 머리말이 과거 날짜뿐 | 보고서를 6일간 7회 개정했으나 머리말은 최초 발행일 그대로 |
| 같은 문서의 판이 배너 없이 7개 병존 | 어느 것을 인쇄해야 하는지 파일명으로 판별 불가 |
| 정본 교체 후 상호 참조 미갱신 | 신판 원페이퍼를 냈는데 상세보고서는 구판을 요약본으로 지목 |
