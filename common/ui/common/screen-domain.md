# 화면 구성 도메인 정의 (UI Screen Domain)

> 📌 **적용 범위**: Flask 웹 화면 설계 공통 규약.
> **각 프로젝트의 실제 화면 목록·시나리오는 이 문서에 두지 않는다.** → `{{guideline.project_dir}}/templates/screen-domain.md`

## 1. 목적

- 각 화면(페이지)의 **도메인(비즈니스 의미)**, **주요 기능**, **필요 데이터**, **상태**를 명확히 정의
- 개발자와 기획자 간 화면 이해를 공유
- 화면 구현 시 일반적인 구조와 사용자 경험 유지

## 2. 프로젝트별 화면 매핑

화면 이름 ↔ URL ↔ 템플릿 파일 매핑표는 **프로젝트 지침**에 둔다. 공통 문서에 특정 프로젝트의 화면 목록을 두면 다른 프로젝트로 복사될 때 그대로 따라가 오염된다.

| 항목 | 위치 |
|------|------|
| 화면 매핑표 | `{{guideline.project_dir}}/templates/screen-domain.md` |
| 화면별 상세 정의 | 동일 |

## 3. 화면 정의 템플릿 (새 화면 추가 시 이 형식 사용)

### 화면 이름: [화면 이름]

**URL**: [예: /dashboard]

**실제 파일**: `[템플릿 경로]/[파일명].html`

**주요 도메인/목적**:
- 이 화면이 해결하는 비즈니스 요구사항

**주요 기능 (Features)**:
- 목록 표시 / 검색·필터 / 생성·수정·삭제 등

**필요 데이터 (Data Requirements)**:
- 백엔드에서 받아올 데이터 모델 및 필드 목록
- 예: `User { id, name, email, created_at, status }`

**화면 상태 (States)**:
- 로딩 / 빈 상태(Empty) / 에러 / 성공

**관련 API 엔드포인트**:
- `GET /api/xxx`, `POST /api/xxx`

**관련 서비스**:
- `<서비스 계층>/xxx_service.py`, `<라우트 계층>/xxx_routes.py` (계층 경로는 `paths.app_root` 아래 실제 구조)

---

## 4. 화면 문제 분석 경로 (공통)

| 요청 성격 | 진입 문서 | 다음 |
|-----------|-----------|------|
| 기능이 동작하지 않음 | `common/core/00-core.md` → 기능 문제 분석/디버깅 | `common/core/03-workflow.md` |
| 디자인 변경 | `common/core/00-core.md` → 공통 UI/디자인 | `common/core/04-design-change.md` |

두 경우 모두 **프로젝트 화면 매핑표에서 실제 파일 경로를 먼저 확정**한 뒤 관련 라우트·서비스로 내려간다. 파일 경로를 추측해서 분석을 시작하지 않는다.
