## 1. 기본 개념

### 1.1 기능점수(Function Point, FP)란?

**정의**  
사용자 관점에서 사용자가 요구하고 사용자에게 인도되는 기능을 정량적으로 산정하는 소프트웨어 규모측정 방법

**핵심 원칙**
- ✅ **사용자 관점 측정**: 사용자가 인식하는 기능만 산정
- ✅ **논리적 설계 기반**: 구현 기술이나 개발방법론과 무관
- ✅ **단계별 측정 가능**: SDLC 전 단계(분석→설계→개발→시험→운영)에서 적용 가능
- ✅ **일관성 있음**: ISO/IEC 20926(CPM - Counting Practice Manual) 표준 기반

### 1.2 기능점수의 장점 vs 단점

| 구분 | 내용 |
|------|------|
| **장점** | • 개발 이전에 공수·사업비 측정 가능<br>• 기술, 공수, 개발방법론에 무관한 일관성<br>• 단계별 재검증 가능 |
| **단점** | • 전문가 필요 (FP 분석 능력 요구)<br>• 화면 없는 데이터 처리/배치 작업에 부적합<br>• 단순 HTML(링크모음 등) 무시<br>• 개발규모 측정에만 집중 (일정, 투입인력은 별도) |

## 2. 기능점수 산정 범위

### 2.1 포함/제외 기준

| 범위 | 포함 여부 | 예시 |
|------|---------|------|
| **기능 요구사항** ✅ | 포함 | 정보등록, 정보출력, 정보조회, 계산, 분석, 통계 |
| **비기능 요구사항** ❌ | 제외(→보정계수로 반영) | 속도, 성능, 보안, 개인정보, 웹표준, 접근성 |
| **사용자 인식 기능** ✅ | 포함 | 메뉴/화면에서 직접 접근 가능한 기능 |
| **상용 솔루션 기능** ❌ | 제외 | OZ리포트, ESB 연계 등 |
| **조건 분기 화면** ⚠️ | 1개만 산정 | 경기/강원/서울 설비현황은 1개로 계산 |

### 2.2 사용자 인식 기능 판단 기준

```
✅ 포함: 요구사항정의서에 명시된 관리자용 기능
✅ 포함: 화면 메뉴에서 직접 접근 가능한 기능
❌ 제외: 접속로그, 시스템성능관리데이터 (비즈니스 데이터 아님)
❌ 제외: 코드성 데이터 (핵심코드, 임시테이블)
```

### 2.3 🔴 FP 인정 안되는 경우 (명백한 제외 대상)

**아래 항목은 "기능"이 아니라 기술 구현이므로 FP 산정 대상이 아닙니다.**

#### A. 상용 솔루션/플랫폼 기능

```
❌ OZ리포트 (리포트 생성)
❌ ESB 연계 (데이터 변환)
❌ ETL 도구 (데이터 이동)
❌ 메시지 큐 (Kafka, RabbitMQ 등)
❌ 캐시 엔진 (Redis 등)

→ 이유: 플랫폼 자체 기능이므로 사용자 요구 기능이 아님
```

**⚠️ 교육자료 L2473-2474 예외 규정 (우선 적용)**

```
"별도 상용SW로 구현되는 기능은 산정하지 않음.
 (단, 결과를 별도로 기록하는 경우는 예외 / 직접 해당 기능을 구현한 경우 예외)"

→ 상용SW를 쓰더라도 그 결과를 자체 ILF에 기록하면 → 해당 트랜잭션은 산정
→ 상용SW에 의존하지 않고 직접 구현했으면 → 산정
```

**⚠️ 선행 확인 의무 — 연계 실체 검증**

솔루션·외부시스템을 EIF 또는 연계복잡도로 산정하기 전에 **반드시 소스에서 실사용을 확인**한다.

| 확인 방법 | 판정 |
|----------|------|
| 소스 grep 결과 0건 | **미존재 → 산정 제외** |
| 주석·문서에만 등장 (코드 출처 표기 등) | **연계 아님 → 산정 제외** |
| DDL만 존재하고 참조 코드 0건 | **미사용 테이블 → 산정 제외** |
| 실제 호출·연동 코드 존재 | 산정 대상 |

> 종전 문서에 기재되어 있다는 이유만으로 승계하지 않는다. **소스가 유일한 근거이다.**

#### B. 시스템 운영 데이터 (비즈니스 데이터 아님)

```
❌ 접속로그 (tb_user_acs_log)
❌ 시스템성능데이터 (CPU, 메모리 등)
❌ API 호출 로그
❌ 에러 로그
❌ 감사 로그 (Audit Log - 규정상 필수는 별도)

→ 이유: 사용자가 직접 조회/수정하지 않는 내부 시스템 데이터
```

**⚠️ 교육자료 L2778 예외 규정 (우선 적용)**

```
"임시테이블, 로그파일, 기술상 도입된 파일 등은 사용자 요구사항에 존재하지 않으므로 식별되지 않음
 (단, 적재된 로그를 조회/분석하는 시스템의 경우는 예외.. 의미있는 사용자 데이터가 됨)"
```

| 로그 성격 | 판정 |
|----------|------|
| 사용자가 화면에서 **조회·분석하는** 로그 | ✅ **ILF 산정** + 조회기능 EQ/EO 산정 |
| 시스템이 기록만 하고 조회 화면이 없는 로그 | ❌ 제외 |

**MSYS 적용**

| 테이블 | 조회 화면 | 판정 |
|--------|----------|------|
| `tb_con_hist_evnt_log` | 대시보드 이벤트로그, API키관리 이벤트이력 | ✅ **ILF 산정** |
| `tb_user_acs_log` | 없음 | ❌ 제외 |
| `tb_api_key_mngr_mail_log` | 없음 | ❌ 제외 |

#### C. 코드성 데이터 (정적, 거의 변경 없음)

```
❌ 상태코드 마스터 (tb_sts_cd_mst)
❌ 아이콘 마스터 (tb_icon)
❌ 공휴일 목록
❌ 지역/부서 코드
❌ 역할(Role) 코드 정의

판정 기준:
- 속성이 2~3개 이하 (예: 코드, 코드명, 색상)
- 레코드 수가 제한적 (30~100개)
- 운영 중 거의 변경 없음
- 하드코딩 가능한 데이터

→ 이유: 개발 초기 설정이지, 사용자가 동적으로 관리하지 않음
```

**⚠️ 코드성 데이터를 유지하는 트랜잭션도 함께 제외 (교육자료 L1454)**

```
"하나의 트랜잭션 기능은 하나 이상의 데이터 기능을 참조한다"

→ 코드성 데이터는 산정 제외이므로 데이터 기능이 아니다.
→ 코드성 데이터만 참조/유지하는 트랜잭션은 참조 데이터기능이 0개가 되어
   식별규칙을 충족하지 못한다. → 데이터와 트랜잭션을 일괄 제외한다.
```

| 대상 | 제외 범위 |
|------|----------|
| 코드성 데이터 | 데이터 기능(ILF) **+ 해당 데이터의 등록·수정·삭제·조회·가져오기·내보내기 트랜잭션 전부** |
| 단, 코드성 데이터 **외에** 다른 ILF를 함께 참조하는 트랜잭션 | 산정 대상 (참조 데이터기능이 존재하므로) |

**MSYS 적용 — 제외 13건**

| 데이터 | 함께 제외되는 트랜잭션 |
|--------|---------------------|
| `tb_icon` | `/icons/save` `/icons/delete` `/icons/toggle-display` `/icons/import` `/icons/all` `/icons/export` |
| `tb_sts_cd_mst` | `/status_codes` `/status_codes/sync` `/status_codes/save` `/api/sts_cd/colors` |
| `tb_menu` | 메뉴 조회 (교육자료 L2810 "메뉴가 DB조회로 보이는 경우 하드코딩과 동일하게 식별하지 않음") |

#### D. 기술 인프라 (사용자 기능 아님)

```
❌ 서버/DB 관리
❌ 네트워크 설정
❌ 보안 인증서 관리
❌ 배포/빌드 자동화
❌ 모니터링 시스템 (Grafana, ELK 등)

→ 이유: 운영 인프라이지 소프트웨어 기능이 아님
```

#### E. 프레임워크 기본 기능

```
❌ 세션 관리 (프레임워크 기본)
❌ 요청/응답 처리
❌ 데이터베이스 연결
❌ 캐싱 (프레임워크 내장)
❌ 로드 밸런싱

→ 이유: 개발 환경 설정이지 사용자 기능이 아님
```

#### F. 공통 모듈 중복 (이미 1회 산정됨)

```
❌ 로그인 기능
   └─ "로그인" 화면에서만 1회 산정
   └─ 다른 화면에서 재사용되어도 추가 산정 안 함

❌ 권한 체크 공통 모듈
   └─ "사용자 권한 설정" 화면에서만 1회 산정
   └─ 9개 블루프린트의 @_required 데코레이터는 중복 제거

❌ 메뉴 접속로그
   └─ "admin 대시보드"에서만 1회 산정

→ 이유: 중복 계산은 비생산성의 역효과
```

#### G. 매개변수화된 단일 기능 (조건 분기)

```
❌ 지역별 설비현황 (경기/강원/서울/부산)
   → 1개의 EQ (조회 화면)로 산정, 4개로 나누지 않음

❌ 기간별 통계 (일/주/월/연)
   → 1개의 EO (통계)로 산정, 4개로 나누지 않음

→ 이유: 사용자 선택에 따른 결과 차이이지 다른 기능이 아님
```

#### H. UI/UX 요소 (기능이 아님)

```
❌ 디자인 변경 (색상, 폰트 등)
❌ 레이아웃 조정
❌ 애니메이션/효과
❌ 반응형 웹 구현
❌ 다국어 지원 (라벨 번역)

→ 이유: 기능의 "어떻게" 구현이지, "무엇"이 아님
```

#### I. 비기능 요구사항 (보정계수로 반영)

```
❌ 성능 최적화 (응답시간 개선)
❌ 보안 강화 (암호화, 인증)
❌ 재해복구 (Disaster Recovery)
❌ 고가용성 (High Availability)
❌ 데이터 마이그레이션

→ 이유: FP 산정 후 "보정계수"로 별도 반영
   예: 암호화 + 시큐어코딩 + 웹취약점검사 = 보안 보정 1.15배
```

#### J. 외부 연계 데이터 참조 (EIF 제외)

```
❌ KEPCO SFTP 설비정보 → EIF (참조만)
   └─ 타 시스템이 관리하므로 ILF가 아님
   └─ 조회(EQ)나 리포트(EO)는 기능, 데이터 자체는 제외

❌ 기상청 API 실시간 데이터
   └─ 외부 연계이므로 내부 관리 불가
   └─ 조회 기능은 EQ/EO로 산정, 데이터는 EIF로만 처리
```

#### K. 화면 렌더링 (대응 API가 이미 산정된 경우)

**교육자료 L1454 + L2744 (중복 판단기준) 적용**

```
L1454 : "하나의 트랜잭션 기능은 하나 이상의 데이터 기능을 참조한다"
L2744 : 트랜잭션 기능 중복 판단 기준
        ① 참조되거나 유지되는 ILF나 EIF가 같은 경우
        ② 경계를 넘나드는 데이터필드가 같은 경우
        ③ 처리 로직이 같은 경우
        → ④ 위 모두 해당하면 중복
L2777 : "세가지 중, 하나라도 아니면 다른 기능으로 식별"
```

| 화면 성격 | 판정 |
|----------|------|
| `render_template()`만 수행, 데이터는 별도 `/api/`가 담당 | ❌ **제외** (참조 데이터기능 0개 + 해당 API와 중복) |
| 화면 자체가 데이터를 조회·가공하여 반환 | ✅ EQ/EO 산정 |
| 테스트/개발 전용 페이지 | ❌ 제외 |

> **원칙: 대응 API가 이미 산정되었으면 화면은 산정하지 않는다.** 동일 단위기능을 두 번 세는 것이기 때문이다.
> 교육자료 L2703은 "최저인 EQ로 산정 권고 / 또는 기능목록상으로만 관리" 두 선택지를 제시하나,

## 3. 기능유형 정의 (5가지)

### 3.1 트랜잭션 기능 (3가지)

트랜잭션: 데이터 처리를 위한 CRUD(Create/Read/Update/Delete)가 발생되는 기능 단위

#### ① EI (External Input - 외부 입력) | **4.0 FP**

**정의**  
애플리케이션 경계 밖에서 들어오는 데이터를 처리하여 **하나 이상의 ILF를 변경**하거나 **시스템 동작을 변경**하는 단위프로세스

**포함 CRUD**: C(Create), U(Update), D(Delete)

**식별 기준**
- 사용자가 입력한 데이터로 ILF 유지
- CUD 중 하나 이상이 발생
- 제어정보로 시스템 동작 변경

**예시 (MSYS)**
- 데이터 정의 등록/수정/삭제
- API 키 등록/수정/삭제
- 사용자 권한 설정/수정
- 팝업 관리 (추가/수정/삭제)
- 메일 스케줄 설정

---

#### ② EQ (External Inquiry - 외부 조회) | **3.9 FP**

**정의**  
데이터를 조회하여 표시하는 **단순 조회** 기능  
(계산/파생데이터 생성/ILF 변경 **없음**)

**포함 CRUD**: R(Read) **만**

**식별 기준**
- 수학 공식 없음
- 파생 데이터 생성 안 함
- ILF 유지 안 함
- 시스템 동작 변경 안 함
- 단순 SELECT 쿼리 결과 출력

**예시 (MSYS)**
- 마스터 목록 조회
- 상세 정보 조회
- 데이터 목록 페이지
- Job 마스터 조회
- 사용자 목록 조회

---

#### ③ EO (External Output - 외부 출력) | **5.2 FP**

**정의**  
EQ(조회)에 **추가로 처리 로직을 포함**하여 데이터를 표시하는 단위프로세스

**추가 처리 로직**
- 계산/통계 (SUM, AVG, COUNT 등)
- 파생 데이터 생성 (그래프, 히트맵 등)
- 여러 ILF의 조인 후 가공

**예시 (MSYS)**
- 대시보드 요약 (집계된 수치)
- 성공률 추이 차트
- 장애코드 비율 분석
- 사용자 접속 통계
- 데이터분석 동적 차트
- 통계 엑셀 다운로드

---

### 3.2 데이터 기능 (2가지)

데이터: 트랜잭션을 발생시키거나 그로인해 변경되는 **논리적 데이터 그룹**

#### ④ ILF (Internal Logical File - 내부 논리 파일) | **7.5 FP**

**정의**  
대상 애플리케이션 **내부에서 생성/유지**되는 사용자 관점의 논리적 데이터 그룹

**핵심**  
- ⚠️ **테이블 1개 = ILF 1개이 아님** → 논리적 데이터셋 개념
- 사용자 관점에서 식별 가능한 데이터
- 해당 시스템의 핵심 비즈니스 데이터

**포함 조건**
```
✅ 업무 요구사항 상 필요한 데이터
✅ 지속 발생/변경되는 데이터 (공고번호, 고객번호 등)
✅ 시스템이 직접 생성/관리하는 데이터
```

**제외 조건**
```
❌ 접속로그, 시스템성능데이터 (시스템 내부용)
❌ 코드성 데이터 (핵심코드, 선택지 목록 - 변경 거의 없음)
❌ 임시 테이블 (작업 중간 데이터)
```

**코드성 데이터 판단**  
다음 중 하나 포함 → 코드성 데이터 (ILF 제외):
- 키, 이름, 약어 등 소수 속성 + 제한적 레코드
- 주소, 양식, 산업분류코드 (하드코딩 가능한 데이터)
- 사용자 변경이 거의 발생하지 않는 데이터

**예시 (MSYS)**
| 데이터 | 판단 | 이유 |
|--------|------|------|
| tb_con_mst (Job 마스터) | ILF | 업무 핵심 데이터, 지속 변경 |
| tb_con_hist (수집이력) | ILF | 핵심 이력 데이터 |
| tb_col_mapp (컬럼 매핑) | ILF | 시스템이 직접 관리하는 설정 |
| tb_sts_cd_mst (상태코드) | ❌ 제외 | 코드성 (선택지 목록, 변경 없음) |
| tb_user_acs_log (접속로그) | ❌ 제외 | 시스템 관리용, 비즈니스 데이터 아님 |

---

#### ⑤ EIF (External Interface File - 외부 인터페이스 파일) | **5.4 FP**

**정의**  
대상 애플리케이션에서 **참조하지만 데이터 유지는 타 시스템이 담당**하는 논리적 데이터 그룹

**핵심**
- 타 시스템/타 기관의 데이터
- 단순 복제 포함 (마스터 데이터 동기화)
- EO/EQ에서만 참조 가능 (**EI에서는 참조 불가**)

**포함 조건**
```
✅ 타 시스템 데이터의 단순 복제
✅ 외부 API 데이터 (기상청, Solcast 등)
✅ SFTP 수신 데이터 (KEPCO 설비정보 등)
```

**ILF vs EIF 판단**

| 상황 | 판정 | 이유 |
|------|------|------|
| 타 시스템 데이터, R/O만 가능 | EIF | 참조만 함 (CUD 없음) |
| 타 시스템 데이터, 복제 후 C/U/D | ILF | EI 발생 → ILF로 전환 |
| 외부 API 메타정보 조회 | EIF | 타 시스템 데이터 참조만 |

**예시 (MSYS)**
| 데이터 | 판단 | 이유 |
|--------|------|------|
| 기상청 API 데이터 (조회만) | EIF | 타 시스템 참조 |
| Solcast 기상예측 | EIF | 외부 API 연계 |
| KEPCO SFTP 설비정보 | EIF | 타기관 데이터 복제 |
| Airflow DAG 정보 | EIF | 외부 시스템 참조 |

```
┌─ 사용자가 데이터를 입력/수정/삭제?
│  ├─ YES → ILF 변경? ──YES──> EI (4.0 FP)

│     ├─ 단순 참조 ──YES──> EIF (5.4 FP)

```

## 4. 기능 식별 규칙

### 4.1 기본 식별 규칙 (Must-Have)

```
✅ 규칙 1: 사용자가 인식하는 기능만 산정
   → 코드 단위 함수가 아닌, 사용자가 메뉴에서 접근하는 기능

✅ 규칙 2: 하나의 트랜잭션 = 최소 1개 이상의 데이터 기능 참조
   → 모든 트랜잭션은 ILF 또는 EIF를 참조해야 함

✅ 규칙 3: 트랜잭션이 없는 데이터 기능은 없음
   → ILF/EIF는 반드시 EI/EO/EQ로 접근 가능해야 함

✅ 규칙 4: 조건으로 분기되는 조회 화면 = 1개만 산정
   → "경기/강원/서울 설비현황" 3가지 → 1개 EQ로 산정

✅ 규칙 5: 상용 솔루션으로 구현된 기능은 산정 안 함
   → OZ리포트, ESB 연계 등 (플랫폼 기능)
```

### 4.2 기능 식별 절차 (5단계)

```
[Step 1] 기능 식별 (대상 기능 목록화)
  → 요구사항정의서, RFP, 기능명세서에서 사용자 기능 추출

[Step 2] 기능유형 구분 (CRUD 분석)
  → 각 기능의 CRUD 작동 파악 (C? U? D? R?)
  → 계산/통계 여부 확인

[Step 3] 기능유형 분류
  → EI, EO, EQ, ILF, EIF 중 하나로 분류

[Step 4] 식별규칙 검증
  → 규칙 1~5 위반 없는지 확인
  → 트랜잭션↔데이터 매핑 검증

[Step 5] 복잡도 산정 & 가중치 적용
  → 간이법: 평균복잡도 → 기본 점수 (4.0, 5.2, 3.9, 7.5, 5.4)
  → 정통법: 개별복잡도 (FTR, DET, RET) → 세부 점수
```

### 4.3 데이터 기능(ILF/EIF) vs 트랜잭션 기능(EI/EO/EQ) 매핑

```
데이터 기능과 트랜잭션의 관계

┌─ ILF 정의 (예: 공고정보)
│  │
│  ├─ 공고등록 (C) ──> EI
│  ├─ 공고정정 (U) ──> EI
│  ├─ 공고취소 (D) ──> EI
│  ├─ 공고목록조회 (R) ──> EQ
│  ├─ 공고상세조회 (R) ──> EQ
│  └─ 공고통계분석 (R + 계산) ──> EO
│
└─ EIF 정의 (예: 기상청 데이터)
   │
   ├─ 기상정보조회 (R) ──> EQ
   └─ 기상분석리포트 (R + 차트) ──> EO

✅ 검증: 모든 데이터는 최소 1개 이상의 트랜잭션으로 접근
```

## 5. 보정계수 적용

### 5.1 보정계수 목적

**"기능점수"는 기능 규모만 측정**  
→ 비기능 요구사항(성능, 보안, 복잡도 등)은 **보정계수**로 반영

```
보정 전 개발비 = FP 합계 × FP당 단가
                (기술 무관, 규모만 반영)

보정 후 개발비 = 보정 전 개발비 × Σ보정계수
                (비기능 요구사항 반영)
```

### 5.2 보정계수 5가지 (한전 표준)

#### A. 규모 보정계수 (Scope - 개발 규모)

**개념**  
개발 사업 규모에 따른 생산성 변화

```
규모가 작음 → 생산성 높음 (1.0 초과)
규모가 중간 → 생산성 기준 (1.0)
규모가 큼  → 생산성 저하 (1.0 이상, 감소 추세)
```

**산정 방법** (교육자료 표3-23 / `temp/images/slide56_img7.png` 원본)

```
규모 보정계수 = 0.4057 × (ln(기능점수) − 7.1978)² + 0.8878

  단, 500 FP 미만시   1.2800 적용
      3,000 FP 초과시 1.1530 적용
```

> `ln` = 자연로그. 500 FP 대입 시 1.2800, 3,000 FP 대입 시 1.1530으로 경계값이 일치함을 검증 완료.
> **500~3,000 FP 구간은 반드시 위 산식으로 계산한다. 1.28을 그대로 쓰지 않는다.**

**참고 계산값**

| 기능점수 | 규모 보정계수 |
|--------:|------------:|
| 500 미만 | 1.2800 |
| 550.7 | 1.2067 |
| 700 | 1.0575 |
| 1,000 | 0.9219 |
| 1,338 (최소점) | 0.8878 |
| 2,000 | 0.9537 |
| 3,000 초과 | 1.1530 |

> 규모가 커질수록 생산성이 올라가 계수가 낮아지다가, 약 1,338 FP를 저점으로 다시 상승하는 U자 곡선이다.

**MSYS 적용**: 550.7 FP → **1.2067**

#### B. 연계복잡도 보정계수 (Integration Complexity)

**개념**  
타 기관/회사 시스템과의 연계 복잡성

```
한전 내부 연계 → 0 (산정 안 함)
타 기관 연계 → +N (해당 개수)
```

**① 연계 개수 판정** (교육자료 슬라이드57)

| 상황 | 개수 산정 |
|------|------|
| 타 기관/회사 시스템과의 연계 없음 | 0 |
| 한전 내부의 타 시스템과 연계 | 산정 안 함 (0) |
| 타 기관/기업 시스템과 연계 존재 | 해당 수량 N |
| 행정정보공동이용센터(행공센) 연계 | 1 |

**② 개수 → 계수 변환** (교육자료 `temp/images/slide57_img6.png` 원본)

| 난이도 수준 | 계수 |
|------------|:----:|
| 1. 타기관 연계 없음 | **0.88** |
| 2. 1~2개의 타 기관 연계 | 0.94 |
| 3. 3~5개의 타 기관 연계 | 1.00 |
| 4. 6~10개의 타 기관 연계 | 1.06 |
| 5. 10개를 초과하는 타 기관 연계 | 1.12 |

**MSYS 적용** — 소스 전수 검증 결과 (2026-07-20)

| 종전 기재 | 소스 검증 | 판정 |
|----------|----------|------|
| Kafka | 소스 0건 | 미존재 |
| KEPCO (SFTP) | 소스 0건 | 미존재 |
| 기상청 (KMA API) | 소스 0건 | 미존재 |
| Solcast | DDL만 존재, 참조 코드 0건 | 미사용 |
| Airflow | 주석(코드 출처 표기)만 존재 | 연계 아님 |

→ 타 기관 연계 **0개** → 수준1 → **0.88 적용**

## 8. 검증 체크리스트

### 8.1 기능 식별 검증

```
□ 모든 기능이 사용자 관점인가?
  → 코드 함수가 아닌, 메뉴/화면 단위 기능인가?

□ 상용 솔루션 기능을 제외했는가?
  → OZ리포트, ESB, 플랫폼 기능 확인

□ 조건 분기 화면을 1개로만 계산했는가?
  → "경기/강원/서울" → 1개 EQ로 산정

□ 접속로그, 임시테이블을 제외했는가?
  → 비즈니스 데이터만 ILF로 포함
```

### 8.2 기능유형 분류 검증

```
□ EI/EO/EQ이 정확히 분류되었는가?
  ├─ EI: CUD 발생 & ILF 변경
  ├─ EQ: R만, 계산/통계 없음
  └─ EO: R + 계산/통계/파생데이터

□ ILF/EIF가 정확히 분류되었는가?
  ├─ ILF: 내 시스템 생성/관리
  └─ EIF: 타 시스템 참조만 (복제는 ILF로 전환)

□ 코드성 데이터를 제외했는가?
  → 핵심코드, 상태코드, 선택지 제외
```

### 8.3 트랜잭션↔데이터 매핑 검증

```
□ 모든 트랜잭션이 데이터 기능을 참조하는가?
  → EI/EO/EQ 모두 ILF 또는 EIF 참조

□ 모든 데이터 기능이 트랜잭션으로 접근 가능한가?
  → ILF/EIF는 EI/EO/EQ로 최소 1회 접근

□ EIF를 EI에서 참조하지 않았는가?
  → EIF는 EO/EQ에서만 참조
```

### 8.4 보정계수 검증

```
□ 규모 보정계수: 500 FP 이상이면 산식으로 계산했는가? (1.28 그대로 쓰면 오류)
□ 연계복잡도: 연계처를 소스에서 실증했는가? (2.3-A 연계 실체 검증)
□ 성능요구: 명시된 성능 요구사항 확인
□ 운영환경: OS/WAS/DBMS 다중성 확인
□ 보안성: 가짓수 판정인가? (항목별 가산 방식 아님)
□ 5개 계수를 곱했는가? (더하기 아님)
```

### 8.5 계산 검증

```
□ FP 합계가 맞는가?
  = Σ(EI수 × 4.0) + Σ(EO수 × 5.2) + Σ(EQ수 × 3.9) 
    + Σ(ILF수 × 7.5) + Σ(EIF수 × 5.4)

□ 단계별 금액 계산이 맞는가?
  = FP × 단계별단가 × 보정계수

□ 총 개발비가 맞는가?
  = 분석금액 + 설계금액 + 구현금액 + 시험금액
```

### 8.6 🔴 정합성 대사 (필수 — 누락·중복 검출)

**산정 건수와 제외 건수의 합이 전수와 일치해야 한다.** 불일치하면 누락 또는 중복이 있다.

```
□ 트랜잭션 :  산정 건수 + 제외 건수 = 소스 추출 전체 건수
□ 데이터   :  ILF + EIF + 제외 테이블 = DDL 테이블 전체 개수
□ 장별 소계 합 = 총계          (각 절 소계를 다시 더해 검증)
□ 유형별 개수 합 = 전체 기능 수
```

**MSYS 대사 예 (2026-07-20)**

| 대상 | 산정 | 제외 | 합 | 전수 | 일치 |
|------|----:|----:|---:|----:|:---:|
| 트랜잭션 (메서드 단위) | 101 | 46 | 147 | 147 | ✅ |
| 데이터 (테이블) | 18 | 6 | 24 | 24 | ✅ |

> 이 대사를 하지 않으면 "대략 60개쯤" 같은 **추정치가 그대로 결과가 된다.** 반드시 수행한다.

### 8.7 🔴 산식 경계값 역산 검증

산식을 적용할 때는 **문서에 명시된 경계값을 대입해 일치하는지 먼저 확인**한다. 일치하지 않으면 산식 해석(로그 밑 등)이 틀린 것이다.

```
규모 보정계수 산식 검증
  500 FP   대입 → 1.2800 이어야 함  (명시 경계값)
  3,000 FP 대입 → 1.1530 이어야 함  (명시 경계값)
  → 두 값이 나오면 자연로그(ln) 해석이 맞음
```

**산출한 참고값도 반드시 재계산 검증한다.** (본 지침 5.2-A 참고표는 검산 완료분)

## 9. FAQ & 주의사항

### Q1: 공통 함수는 어떻게 계산하는가?

**A:** 공통 함수는 **1회만 산정** (위치는 가장 먼저 사용하는 곳)

```
예시: 로그인 공통 모듈
- 모든 화면에서 사용되나, 로그인 화면의 EI로만 1회 산정
- 다른 화면에서는 중복 계산 안 함
```

### Q2: 배치 작업(Job)은 기능으로 산정하는가?

**A:** **비즈니스 가치 있는 최소 단위(Job) = 1개 기능**

```
例) 일일 데이터 수집 배치
Step1: 외부 API 호출
Step2: 데이터 파싱
Step3: DB 저장
→ 이 3단계 = 1개 EI로 산정 (Step 단위가 아님)
```

### Q3: 화면이 없는 REST API는?

**A:** **사용자가 인식 불가** → 산정 제외

```
예외) 관리자/개발자 도구 → 명시된 요구사항이면 포함
```

### Q4: 추가 개발 시 FP 재산정은?

**A:** **변경된 부분만 재측정** (개선프로젝트 모드)

```
개발프로젝트: 전체 기능 측정
개선프로젝트: 변경 부분만 측정
유지보수: 현행 애플리케이션 측정 (유지관리 비용 산정)
```

| 인증 방식 | 인증 구현 소스 | "SSO 로그인"으로 기재되어 있었으나 실제는 자체 ID/PW 인증 |
| 개발기간 | 형상관리 이력, 착수 공문 | 참고문서(1.pdf)의 날짜가 **그대로 복사**되어 있었음 |
| 보정계수 | 대가산정 가이드 원본(교육자료 이미지 포함) | 500 FP 미만 기준 1.28이 **500 FP 초과 사업에 그대로** 적용되어 있었음 |
| 정량효과 | 실측 데이터 | 근거 없는 절감액·ROI·오류감소율이 기재되어 있었음 |

> **판정**: 원천에서 확인되지 않으면 **기재하지 않는다.** "종전 문서에 있었다"는 이유로 남기지 않는다.

### 11.8 🔴 참고문서 취급 원칙

타 사업 보고서(예: `1.pdf` ICT설비관리시스템 구축완료보고)를 참고할 때:

| 참고 가능 | 참고 금지 |
|----------|----------|
| ✅ 문서 구조·장 구성 (본문 4개 항 + 붙임1·2) | ❌ 개발기간·투입인원 |
| ✅ 표 양식·레이아웃 | ❌ 기능 목록·기능점수 |
| ✅ 항목 명칭 (「구축배경」「개발내용」 등) | ❌ 금액·보정계수 값 |
| ✅ 서술 어투 (□ 기호, 개조식) | ❌ 기대효과 문구·수치 |

> **참고문서는 양식만 가져온다. 내용은 한 글자도 가져오지 않는다.**
> 작성 후 참고문서와 **날짜·금액·인원이 우연히 일치하는 항목이 없는지 대조**한다. 일치하면 복사된 것이다.

### 11.9 산정 결과 변경 시 기록

FP 산정치가 변경되면 **내부 검토의견 문서에 변경 사유를 기록**한다.

```
| 구분 | 종전 | 정정 | 변경 사유 |
```

- 유형별 개수 변동과 그 원인을 각각 기재한다.
- 변경으로 인한 **개발비 영향액**을 함께 기재한다.
- 평가 단계에서 이의가 예상되는 항목은 **쟁점**으로 명시하고 변동 범위(시나리오별 FP)를 제시한다.

### 11.10 원천 자료 판독 범위

교육자료·가이드의 **본문 텍스트만으로 판단하지 않는다.**

| 자료 형태 | 처리 |
|----------|------|
| 본문 텍스트 | 기본 판독 |
| **첨부 이미지** (`temp/images/*.png`) | **필수 판독** — 보정계수표·단가표는 대부분 이미지 |
| 표가 깨져 추출된 부분 | 원본 슬라이드 이미지로 재확인 |

> 본 지침의 보정계수 5종과 FP당 단가는 **전부 이미지에만 존재**했다. 텍스트만 읽으면 "미명시"로 오판한다.
