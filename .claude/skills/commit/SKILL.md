# 커밋 절차 스킬 (/commit)

사용자가 커밋을 명시적으로 요청했을 때만 이 절차를 실행한다. 커밋 요청이 없는 작업 완료 시점에 선제적으로 커밋하지 않는다.

## 공통 안전 규칙 (모든 프로젝트, 예외 없음)

1. **파괴적 git 명령 금지**: `git reset --hard`, `git checkout -- .`, `git clean` 등은 실행하지 않는다 (전역 deny 설정으로도 차단됨).
2. **hook 우회 금지**: pre-commit hook이 커밋을 중단시키면 `--no-verify`로 우회하지 말고, hook이 요구하는 조치(문서 동기화 등)를 조사해 사용자에게 보고한다.
3. **push는 사용자가 명시 요청한 경우에만** 실행한다.
4. **저장소 소속 확인 선행**: 커밋 전에 변경 파일이 어느 저장소 소속인지 확인한다 — root 저장소 vs 서브모듈 vs 서브폴더의 별도 저장소(`git -C <폴더> remote -v`로 확인). 서브모듈 변경은 서브모듈 저장소에서 먼저 커밋하고, root의 SHA 업데이트는 그 다음에 커밋한다.
5. **논리 단위 커밋**: 서로 무관한 변경을 한 커밋에 섞지 않는다. 요청 범위 밖의 미커밋 파일은 커밋에 포함하지 말고 잔여 목록으로 보고한다.

## 절차 분기

### 분기 A — CR 관리 프로젝트 (`.clinerules/common/core/06.git-rules.md`가 존재)

이 파일이 존재하면 **그 문서가 커밋 절차의 정본**이다. 반드시 읽고 그대로 따른다. 이 스킬에는 절차를 복제하지 않는다(이중 관리 방지) — 아래는 누락 방지용 체크포인트 요약일 뿐이다:

- 프로젝트에 `cr-scribe` 서브에이전트(`.claude/agents/cr-scribe.md`)가 정의되어 있으면 **커밋 작업 전체를 그 에이전트에 위임**한다.
- 직접 수행하는 경우 체크포인트:
  1. CR ID 채번 — `.clinerules/docs/cr/` 조회 후 다음 번호(`REQ-yymm-nnn`) 부여, 결과 즉시 보고
  2. 작업 유형 판정 — 기능(feat/refactor: FP 산정) vs 비기능(fix/inquiry 등: 실투입 시간 H)
  3. CR 보고서 작성 — `.clinerules/docs/cr/REQ-yymm-nnn.md`
  4. 커밋 메시지 — `REQ-yymm-nnn: <50자 요약>` + 상세 불릿 + `Refs`/`FP`/`공수`/`작업유형` 푸터
  5. 기능 작업이면 릴리즈 노트(`REQ-yymm-nnn-r.md`) 추가
  6. 커밋 순서 — `.clinerules/` 변경분은 `.clinerules/` 저장소에 먼저, root의 서브모듈 SHA 업데이트는 나중에

### 분기 B — 일반 프로젝트

1. `git status`와 `git diff`(staged/unstaged)로 변경 전체를 파악한다.
2. `git log --oneline -10`으로 프로젝트의 커밋 메시지 관례를 확인하고 그 형식을 따른다.
3. 커밋할 파일만 선별해 `git add` 후 커밋한다.

## 완료 보고

- 커밋한 저장소·커밋 해시·메시지 요약
- 생성한 문서 경로 (CR 보고서·릴리즈 노트 등, 해당 시)
- hook 실행 결과 (자동 산출물 갱신·검사 통과 여부, 해당 시)
- **커밋하지 않은 잔여 변경 파일 목록을 정직하게 고지**
