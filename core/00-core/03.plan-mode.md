# 📌 Plan Mode 규칙

## Plan Mode이란?

- Plan mode에서는 **읽기만**
- 실행은 "수행"이라고 **명시적으로 요청**할 때까지 대기

## 계획서 작성 규칙

Plan Mode에서 사용자가 계획서(또는 설계 문서, 상세 계획) 작성을 요청한 경우:

1. **저장 위치**: 프로젝트 루트 기준 `wordcloud_project/plans/YYYY/MM/` 연도·월별 폴더 아래, **작업별 하위 폴더**를 생성하여 저장한다.
   - 연도별 폴더명: `YYYY/` (예: `2026/`)
   - 월별 폴더명: `MM/` (2자리, 예: `06/`)
   - 작업 폴더명: `DD_NN_작업명/` (파일명과 동일)
   - 모든 계획 문서는 해당 작업 폴더 내부에 저장
   - 예: `D:\dev\wordcloud\wordcloud_project\plans\2026\06\05_03_deploy-retry-cascade\`

2. **파일명 형식**: `DD_NN_작업명.md` (작업 폴더명과 동일 — 파일명=폴더명 규칙 유지)
   - `DD`: 작성일 일(2자리, 예: `05`)
   - `NN`: 당일 동일 작업의 순번 (01, 02, ...)
   - `작업명`: 하이픈(-)으로 연결된 영문 소문자, **최대 20자**
   - 예: `05_03_deploy-retry-cascade.md`
   - 월(`MM`)은 상위 폴더명으로 구분되므로 파일명에는 포함하지 않음
   - 작업 폴더 내 정렬 시 `DD_NN` 순으로 최신이 하단에 배치

3. **파일 내용**: 반드시 마크다운 형식. 최상단에 제목, 작성일시, 작업 유형, 상태 기재

4. **승인 절차**: 사용자가 "수행"으로 명시적 요청 전까지는 파일 시스템에 **저장만** 하고 실제 코드 변경은 하지 않음

5. **사용자 알림**: 계획서를 사용자에게 안내할 때, 대화창 마지막에 반드시 **파일 전체 경로**와 **파일명**을 함께 출력
   - 예: `계획서 저장 위치: D:\dev\wordcloud\wordcloud_project\plans\2026\0605_03_deploy-retry-cascade\0605_03_deploy-retry-cascade.md`

6. **상태 관리**: 계획서 상태는 **단일 파일 내 인라인으로 관리**한다. 별도 복사본 파일을 생성하지 않는다.
   - 상태 약어:
     - `Todo`: 대기/예정 → Kanban **Todo**
     - `Doing`: 분석/검토 진행 중 → Kanban **Doing**
     - `Pre-Done`: 구현·단위검증 완료, 최종 점검 대기 → Kanban **Pre-Done**
     - `Done`: 작업 완료 — 실제 구현/적용 완료 → Kanban **Done**
     - `Hold`: 의도적 미적용·결정 대기로 **종결**한 항목 — 완료가 아닌 보류 종결. `Done`과 명확히 구분
     - `Drop`: 잘못 작성되었거나 전제가 틀려 **폐기**한 계획서 — 추진하지 않음. `Hold`(나중에 재개 가능)와 달리 되살리지 않음
   - 상태 흐름: `Todo` → `Doing` → `Pre-Done` → `Done`
   - 상태는 문서 최상단 메타 블록에 한 줄로 표기:
     - 예: `> 상태: Todo | 작성일: 2026-06-05`
     - 예: `> 상태: Done | 완료일: 2026-06-05`
      - 예: `> 상태: Hold — 사유 | 작성일: 2026-06-05`
      - 예: `> 상태: Drop — 사유 | 작성일: 2026-06-05`
    - 메타블록 선택 필드 (자기완결 미러용):
      - `완료일:` — 값 형식 `YYYY-MM-DD`, 헤더 25줄 이내 배치. Done 상태의 실제 종료일 표준 메타 필드.
      - `관련 CR:` — `REQ-XXXX-NNN`(복수 콤마+공백). 정본은 `_index.md` 컬럼, 메타블록은 선택 미러.
      - `선행:` — 계획 좌표 `YYYY/MM/DD_NN`(동월은 `DD_NN`). 정본은 `_index.md` 컬럼, 메타블록은 선택 미러.
      - `에픽:` — 영문 슬러그. 정본은 `_index.md` 컬럼, 메타블록은 선택 미러.

7. **수정 이력 관리 (인라인 히스토리)**: 계획서에 수정/재검토 사항이 발생한 경우 별도 파일 생성 없이 단일 파일 내에서 관리한다.
   - 문서 최상단(메타 블록 바로 아래)에 `## 수정 이력` 섹션을 두고 **요약 테이블**로만 기록한다.
   - 이전 수정 요청의 상세 내용은 요약 테이블 한 줄로 압축하고, 문서 내 해당 섹션을 최신 내용으로 직접 교체한다 (이전 전체 내용 복사 금지).
   - 현재 수정 요청 상세 내용은 문서 내 별도 섹션으로 전체 기록한다.
    - 완료 시 수정 이력 섹션은 그대로 보존하고 상태만 `Done`으로 변경한다.

   ```markdown
   ## 수정 이력

   | 날짜 | 변경 섹션 | 변경 요약 |
   |------|-----------|-----------|
   | 2026-06-05 | §3 구현 방식 | retry API 엔드포인트 경로 변경 |
   | 2026-06-05 | §5 결함 목록 | 결함 2 (sessionId 누락) 추가 |
   ```

8. **인덱스 (`_index.md`) 관리**:
   - **월별 `_index.md`가 단일 정보원**이다. `YYYY/MM/_index.md` 를 각 월마다 유지하며, 칸반보드는 이 월별 파일들을 병합(`parse_all_months`)하여 표출한다(계획서 `10_01` 참조).
   - 연도 루트 `YYYY/_index.md`는 **필요 없으며 생성하지 않는다**(월 파일 완성 후 삭제, 드리프트 방지). 과거 호환용 병합본이 필요하면 월 파일에서 생성하되 칸반 정보원으로 삼지 않는다.
   - `_index.md`는 탐색기 정렬 상단 고정을 위해 언더스코어 prefix를 사용한다.
   - **계획서 작성, 상태 변경(Todo→Pre-Done→Done), 수정 이력 추가 시 반드시 해당 월 `_index.md`를 동시에 업데이트한다.**
   - 월별 폴더 최초 생성 시 `_index.md`도 함께 생성한다.

     ```markdown
    # 2026 계획서 인덱스

      | 계획서 | 작업 요약 | 상태 | 작성일 | 관련 CR | 선행 | 에픽 |
      |--------|-----------|------|--------|---------|------|------|
     | 0605_03_deploy-retry-cascade | 실패 태스크 cascade retry | Todo | 2026-06-05 |
     | 0605_02_deploy-ux-enhance | 저장 완료 후 UX 개선 | Done | 2026-06-05 |
     | 0602_01_profanity-eng-fix | 불용어 영문 처리 개선 | Done | 2026-06-02 |
    ```

    **3링크 컬럼 규칙 (`관련 CR`, `선행`, `에픽`)**: `관련 CR` = CR 요청서 ID(`REQ-\d{4}-\d{3}`), 복수는 콤마+공백 구분. `선행` = 동월 `DD_NN` 또는 타월 `YYYY/MM/DD_NN`. `에픽` = 영문 소문자 하이픈 슬러그. 값 없으면 빈칸(간선 없음), 확인된 없음은 `-`.

    **상태 컬럼 규칙 (Kanban 파싱 일관성)**:
    - 상태값은 **약어만** 사용: `Todo`(대기/예정) / `Doing`(분석중) / `Pre-Done`(최종 점검 대기) / `Done`(완료) / `Hold`(보류) / `Drop`(폐기)
    - `Hold`는 "구현하지 않기로 결정했거나 외부 결정·승인 대기"인 항목에 사용하며, **실제 구현 완료(`Done`)와 반드시 구분**한다. Kanban 보드의 `📌 Hold` 컬럼으로 분류된다.
    - `Drop`은 "잘못 작성되었거나 전제가 틀려 추진하지 않는" 계획서에 사용하며, **다시 되살리지 않는다는 점에서 `Hold`와 구분**한다. Kanban 보드의 `🗑️ Drop` 컬럼으로 분류된다.
    - Emoji(`✅`, `🔄`, `🔶`, `📋`, `📌`, `🗑️`)를 상태 컬럼에 **절대 포함 금지** — Kanban 보드의 UI 레이어가 자동 표시
    - 상태 컬럼 이외의 컬럼(계획서, 작업 요약, 작성일)도 emoji 사용 금지
    - 위 6개(`Todo`, `Doing`, `Pre-Done`, `Done`, `Hold`, `Drop`) 외 미등록 토큰을 쓰면 해당 행이 Kanban 파서(`src/routes/plans_routes.py` `TABLE_RE`)에 매칭되지 않아 **보드에서 누락**된다 → 반드시 등록된 약어만 사용

9. **연도 폴더 기준**: 계획서가 속하는 연도는 **작성일** 기준으로 고정한다. 2026년에 작성해 2027년에 완료되어도 `2026/`에 유지한다.

10. **계획 문서 기반 테스트 및 결과 관리**: 계획서 기반으로 구현 시 테스트가 필요한 경우, 해당 작업 폴더 안에 `test/` 하위 폴더를 생성하여 테스트 코드 파일을 저장한다. 테스트 완료 보고서 및 리포트는 동일 폴더 안에 `result/` 하위 폴더를 생성하여 저장한다.

11. **함수/클래스 정보 확인 규칙 (예측 금지)**:
    - 계획서에 언급하는 모든 함수, 클래스, 메서드, 변수명은 **반드시 실제 코드베이스에서 검색/확인**한 후에만 작성한다.
    - 파일명을 보고 "있을 것 같다" 또는 "다른 프로젝트에서 이렇게 했으니 여기도 있을 것" 같은 **추측(predict) 금지**.
    - 확인 방법: `grep` 도구로 함수명 검색, `read` 도구로 파일 직접 열어 확인.
    - 존재 여부만 확인하지 말고, **실제 함수 시그니처, 반환값, 동작 방식**까지 읽고 기술한다.
    - 함수가 존재하지 않을 경우: "해당 함수는 현재 코드베이스에 존재하지 않음 — 신규 생성 필요"라고 명시한다.

12. **DB/경로/설정 정보 확인 규칙**:
    - DB 경로, 초기화 위치, 설정 파일 위치 등 인프라 정보는 **실제 코드에서 경로 문자열을 검색**하여 확인한다.
    - "아마도 ~에 있을 것" 같은 표현 금지. 정확한 파일 경로와 코드 인용을 함께 제시한다.
    - 예시 구조:
       ```
        plans/
        └── 2026/
            ├── _index.md
            └── 0605_03_deploy-retry-cascade/
                ├── 0605_03_deploy-retry-cascade.md
                ├── test/
                │   └── test_retry_cascade.py
                └── result/
                    └── 완료보고_260605-1500.md
       ```

13. **버그/디버깅 계획서는 "증거 우선"·"원인 확정 게이트" 적용 (필수)**:
    - **분류 규칙**: 과거 정상 동작하던 기능이 지금 오동작하면 **무조건 버그(A)**다. 수정에 코드가 추가되더라도 기능개선(B)으로 분류해 버그 템플릿의 재현·근거 규율을 우회하지 말 것.
    - **증상 → 원인 순서 고정**: 계획서는 *관찰된 실패 산출물(실제 에러·로그·실패 입력)*에서 출발한다. 추정 원인에서 출발해 그걸 정당화하는 방향으로 작성하는 것은 지침 위반.
    - **원인 확정 게이트**: 원인은 ① 실제 파라미터로 재현, ② 지목한 코드 줄이 그 실행에서 나쁜 값을 만든다는 관측, ③ 반증 실험 — 3개를 모두 충족할 때만 "원인"으로 적는다. **"코드 존재 확인(grep) ≠ 원인 확정"**. 게이트 통과 전 수정 구현 금지. 상세는 `03-plan-mode/type-a-bugfix.md` §1~§2.
    - **실패 사례 참조**: `wordcloud_project/plans/2026/0625_01_eval-pseudonym-double-mapping-fix`(가명화를 원인으로 오진 → 실제는 날짜 필터 버그). 본문+"🔄 반전"을 함께 읽어 오진 패턴을 익힐 것.

14. **요구사항 원자화 및 답변 대장 (필수)**:
    - **목적**: 사용자 요구를 해석 오차 없이 못 박고, "구현했다는데 실제로 그런가"의 간극을 없앤다. 요구를 **초등학생도 이해할 수 있는 원자 질문**으로 쪼개 계획서에 적고, **재확인** 후 작업하고, **작업 후 각 질문에 실측 답을 단다.**
    - **원자 질문의 조건**:
      - **하나의 검증 가능한 사실**만 담는다(Yes/No 또는 단일 값). "그리고/또는"으로 두 가지를 묶으면 위반 → 쪼갠다.
      - 애매어(적용/처리/반영 등) 금지. **어디서·무엇이·어떻게 되는지**를 구체적으로 쓴다. (나쁜 예: "저장되는가?" → 좋은 예: "게시판에서 저장하면 **DB가 아니라 패킷 파일**에 써지는가?")
      - 사용자 원문 질문/요구를 상위 항목(1, 2, …)으로 두고, 그 아래 원자 질문(1.1, 1.1.1 …)으로 계층 분해한다.
    - **계획서 배치**: 메타 블록·수정 이력 다음에 `## 요구사항 원자화` 섹션을 **표**로 둔다. 컬럼: `# | 원자 질문 | 기대(사용자 확인) | 작업 후 답 (근거)`.
      - `기대`는 재확인 단계에서 사용자가 확정한 값. `작업 후 답`은 구현·검증 후 채우며 **반드시 근거를 병기**한다(`파일:라인`, 실측 로그, 테스트명). 미검증이면 `미검증(사유)`로 남기고 빈칸 금지.
    - **절차**: (a) 요구 접수 → 원자 질문 표 작성 → (b) **재확인**: 각 원자 질문에 대해 **내가 이해한 예측 답(기대값)을 먼저 채워** 사용자에게 제시하고 "이 질문들이 맞는지, 그리고 제가 이해한 답이 맞는지" 확인받는다(내 해석이 요구와 어긋났는지 여기서 걸러낸다) → (c) 확정분으로 구현 → (d) 완료 후 각 행 `작업 후 답`을 실측 근거로 기입. **기대와 답이 불일치하면 Done 불가**(수정 또는 사용자 재확인).
      - 예측 답을 비워두고 사용자에게 "어떻게 할까요"만 던지지 않는다. **먼저 내 이해를 답으로 제시**해 사용자가 O/X만으로 교정할 수 있게 한다(결정이 갈리는 항목만 선택지를 병기).
    - **비례 원칙**: 요구가 단순하면 원자 질문 1~2개로 족하다. 다만 **오해 소지·다중 해석·상태/경로가 얽힌 요구는 원자화 필수**.

    ```markdown
    ## 요구사항 원자화

    | # | 원자 질문 | 기대 | 작업 후 답 (근거) |
    |---|-----------|------|------------------|
    | 1.1.1 | 그룹검토 검토 파일 목록에서 이 패킷을 선택할 수 있는가? | Y | Y — /group-review/files가 패킷 노출 (perspective_routes.py:1680) |
    | 1.1.2 | 그 파일을 기존 게시판 형태로 열어 사용자가 수정 가능한가? | Y | Y — load가 status==2 행 매핑, 게시판 JS 무변경 (:1708) |
    | 1.1.3 | 사용자가 수정하면 DB가 아니라 패킷 파일에 저장되는가? | Y | Y — save→update_packet_decisions 파일 기록, DB 미접촉 (:1760) |
    ```

15. **자기완결성 — 컨텍스트 없는 독자(저비용 모델 포함)도 실행 가능하게 (필수)**:
    - **목적**: 계획서는 **작성한 세션의 기억 없이 이 문서 하나만 읽고 실행**할 수 있어야 한다. 작성 AI의 세션 컨텍스트(대화 이력·개인 메모리·직전 탐색 결과)에 기대 축약하면, 다른 담당자나 저비용 모델이 파일을 못 찾거나 수치를 다르게 세어 그대로 따라오지 못한다.
    - **경로**: 참조하는 모든 파일·폴더는 **저장소 루트 기준 전체 경로**로 적는다. 축약이 불가피하면 문서 상단에 축약 규약을 **1회 정의**하고(예: `DS/ = wordcloud_project/plans/_datasets/kote_finetune/`) 그 뒤부터만 사용한다. "그 파일", "위 스크립트" 같은 대명사·지시어 참조 금지.
    - **수치**: 인용하는 모든 수치(행수·건수·비율)는 **작성 시점에 원본을 재집계**해 적고, **산식/필터 조건**을 병기한다. 다른 문서(이력·이전 스냅샷)의 수치를 재확인 없이 승계 금지. (예: "긍↔부 12행 = `label_audit_prefill_260708.jsonl`의 `proposal==change` 중 `{gold, claude_judgment}=={positive,negative}`" — 같은 파일도 `conflict_labels` 필드로 세면 2가 나오므로 **어느 지표인지 못 박는다**.)
    - **원칙·근거의 인라인화**: 판단 근거가 되는 원칙은 `[[메모리슬러그]]` 링크가 아니라 **본문에 한 줄로 서술**한다. 위키 링크는 작성 AI의 세션 메모리를 가리켜 저장소에서 해소되지 않는다. 링크를 남기려면 반드시 그 옆에 **요지를 함께** 적는다.
    - **기존 자산 확인**: "신규 작성/생성"이라고 쓰기 전에 동일 목적 파일이 이미 있는지 `glob`/`grep`으로 확인한다(#11·#12의 확장). 있으면 "기존 X 실행/보완"으로 적는다.
    - **자기검증 체크(작성 후)**: ① 경로만 보고 파일에 도달 가능한가 ② 수치를 제3자가 재집계해 같은 값이 나오는가 ③ `[[...]]` 잔존 없는가 ④ "작성/기존" 표기가 실측과 맞는가.
    - **참조 사례**: `wordcloud_project/plans/2026/07/13_02_model-next-cycle/13_02_model-next-cycle.md` — §8(복수 AI 검토)·§9(실측 재검증)에 축약 경로·승계 수치·세션 메모리 링크가 어떻게 오독을 유발했고 어떻게 정정했는지 기록되어 있다. 자기완결성 위반의 구체 예시로 참고할 것.

16. **실행 로그와 상위 AI 확인 (저비용 모델이 계획서를 실행할 때 필수)**:
    - **적용 대상**: 계획서에 따라 실제 작업을 수행하는 실행 주체 — 특히 **저비용/소형 모델**. 스스로 "완료"를 단정하지 말고, 아래 로그·확인 절차를 반드시 거친다.
    - **실행 로그 의무**: 계획서 하단에 `## 실행 로그(수행일·작업자)` 섹션을 만들고, ① 수행한 **명령어 원문** ② 입력 파일 **전체 경로** ③ 산출물 **전체 경로** ④ 핵심 **수치**를 기록한다. 각 수치는 **어떤 명령/필터로 집계했는지** 병기해 제3자가 재집계할 수 있게 한다(#15 자기완결성 준용).
    - **기억 금지·산출물 집계**: 수치는 "~건 처리했다"는 기억이 아니라 **산출 파일에서 실제로 집계한 값**으로 적는다. 로그의 수치와 산출 파일이 **일치해야** 하며, 합계·부분합의 산술 정합(부분합의 합 = 총계)을 스스로 검산한다.
    - **불확실·편차 표시**: 규칙 해석이 갈리거나 **데이터 현실이 계획과 다른 지점**(예: 계획은 "필드 층화"인데 데이터에 필드가 없음)은 임의로 결정하지 말고 로그에 **"편차/불확실"로 명시**해 상위 AI·사용자가 판단하게 한다.
    - **상위 AI 확인 요청(escalation)**: 실행을 마치면 스스로 상태를 `Done`으로 올리지 말고 **`Pre-Done`에 두고 상위(고성능) AI에게 검토를 요청**한다. 요청 시 ⓐ 무엇을 했는지 ⓑ 산출물 경로 ⓒ 검증이 필요한 핵심 수치·판단을 명시한다. 상위 AI가 **산출 파일을 실측 대조**해 통과시킨 뒤에만 `Done`으로 승격한다.
    - **상위 AI의 검토 의무**: 검토자는 실행 로그의 수치를 **믿지 말고 산출 파일에서 재집계**해 대조한다(로그 수치·산술 정합·계획 부합). 결과는 계획서에 검토 섹션으로 남겨 감사 추적(audit trail)을 만든다.
    - **참조 사례**: `13_02_model-next-cycle.md` §11(실행 로그)·§12(상위 AI 검증) — 실행 로그의 escalation 세부 수치 오기(부분합의 합 101 ≠ 총계 74)와 low_margin 티어 오염(점수없음 행 혼입)이 상위 AI의 산출물 재집계로 적발된 실제 예시.

17. **역할군 분리 — 저비용/고비용 AI 담당 명시 (필수)**:
    - **목적**: 계획서의 각 작업을 어느 등급 AI가 수행할지 명시한다. **핵심은 "검증 비용이 실행 비용을 넘지 않게" 나누는 것**이다. 잘못 나누면 고비용 AI의 검증이 사실상 **재계산(=실행 재현)**이 되어 토큰 절감 효과가 사라지거나 역효과가 난다.
    - **분리 원칙 (검증가능성 기준)**:
      - **고비용 AI 역할군**: ① 계획 설계·성공기준·**데이터 함정 사전점검**(예: 입력에 미채점 행이 섞였는지) ② **자기검증 스캐폴딩 작성** — 수치를 스스로 집계·산술검산·출력하는 스크립트, assert/불변식, gold·테스트 정의 ③ 판단이 갈리는 케이스·**핵심가치(긍↔부) 영향 판정** ④ 저비용 산출물 검증(**재계산이 아니라 자기검증 출력 확인**).
      - **저비용 AI 역할군**: ① 고비용이 만든 **자기검증 스크립트를 대량 데이터에 실행** ② 항목당 저위험 대량 prefill·라벨링 ③ **스크립트가 출력한 수치를 그대로 로그에 기록**(손으로 집계·추정 금지) ④ 가드레일 밖 케이스는 escalation.
    - **황금 규칙**: 저비용 AI는 **고비용 AI가 재계산해야만 검증되는 수치·판단을 손으로 생성하지 않는다.** 모든 수치는 자기검증 스크립트가 산출·검산해 출력한다. 그래야 고비용 검증이 "출력 확인"(저렴)이지 "전량 재현"(비쌈)이 아니다.
    - **계획서 표기**: 각 단계·작업 행에 담당 등급을 `[저]`/`[고]`로 태그하거나 별도 "역할 분담" 표를 둔다(`§실행 순서`의 각 노드에 담당 명시).
    - **안티패턴(회피)**: **핵심 구현·집계를 저비용에 맡기고 고비용이 결과만 검증** → 검증이 재계산이 되어 절감 0 또는 역효과. (실측 사례: `13_02` §12 — escalation 수치·low_margin 오염 검증에 고비용 AI의 산출물 전량 재집계가 소요됨. 올바른 분리였다면 스크립트가 검산 라인을 출력하고 고비용은 그 한 줄만 확인.)

18. **문서 간 연결(링크 그래프)** — 계획서들은 더 이상 독립 섬이 아니다. 문서 간 연결 고리를 `_index.md` 기반으로 구성한다.
    - **링크 3종**: `_index.md` 컬럼 `관련 CR`(계획→CR), `선행`(계획→계획 의존), `에픽`(동일 태그 묶음). 값 형식 — `관련 CR`: `REQ-\d{4}-\d{3}`(복수 콤마+공백). `선행`: 동월 `DD_NN` 또는 타월 `YYYY/MM/DD_NN`. `에픽`: 영문 소문자 하이픈 슬러그. 빈칸=간선 없음, `-`=확인된 없음.
    - **단일 출처 원칙**: 정본(正本)은 **`_index.md` 컬럼**이다. 계획서 메타블록은 자기완결용 선택 미러다. 충돌 시 _index.md가 우선한다.
    - **작성 게이트(AI 필수 채움)**: 계획서 작성 시 AI는 ① 본문 `REQ-XXXX-NNN` grep + CR_DIR 실존 대조로 `관련 CR` 후보 ② 현 작업의 파생 관계로 `선행` 후보 ③ 기존 에픽 태그 재사용 제안을 자동 탐지·기입하고, 사용자 O/X 확정을 받는다. 확인된 없음은 `-`, 미확인은 빈칸. 미확인 필드가 남은 채 `Done` 금지.
    - **린터(Done 전환 게이트)**: 검증 가능한 위반만 담당 — ① `관련 CR`·`선행` 좌표 실존(dangling 금지) ② 선행 DAG(순환 없음). 위반 시 Done 차단. 빈칸·미확인 판정은 하지 않는다(텍스트상 구별 불가 = 작성 게이트 전담).
    - **복합 그래프 예외**: 링크 3개 이상인 계획만 `## 관계` 표로 계획서 본문에 승격한다(`_index.md` 평탄 컬럼으론 과밀).
    - **소급(백필)**: 과거 계획은 스크립트가 후보만 제시, 사용자 확인 후 반영. 자동 커밋 금지.

## Git 커밋/푸시 시 `.clinerules` 지침 파일 취급 규칙

> ⚠️ **협업 보존 규칙**: 다른 팀원이 `.clinerules`를 동시에 작업할 수 있으므로, 반드시 아래 규칙을 준수한다.

1. **교체 금지**: `.clinerules/` 하위 파일을 커밋할 때, **파일 전체를 교체(replace/overwrite)**하지 않는다.
2. **차이 확인**: 푸시 전 `git diff HEAD~1 -- .clinerules/` 또는 `git show origin/master:.clinerules/파일명`으로 원격 내용과 비교한다.
3. **추가 방식**: 기존 내용이 유지된 상태에서, **우리가 추가한 항목만 Append** 하는 방식으로 커밋한다.
4. **삭제 방지**: 기존 지침의 섹션, 규칙, 문맥이 **삭제되거나 누락되지 않도록**, `git diff --cached -- .clinerules/`로 변경 내역을 반드시 검토한다.
5. **충돌 대응**: 원격 파일과 로컬 파일이 다를 경우, `git merge` 방식으로 양쪽 내용을 병합한 후 커밋한다. 병합 불가 시 사용자에게 보고한다.
