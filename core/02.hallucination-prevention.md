# 02. Hallucination Prevention & Verification Rules (환각 방지 및 검증)

## 핵심 원칙

**Claude가 스스로 만든 정보를 마치 존재하는 것처럼 처리하는 환각(Hallucination) 행위를 철저히 방지한다.**

사용자가 비교분석, 영향도 분석, 현황 정리 등을 요청할 때, Claude는 반드시 **원본 문서/코드를 직접 읽고 검증한 후에만** 결과를 작성해야 한다.

---

## 1️⃣ 비교분석 작성 규칙

### 규칙: 원본 검증 의무화

**금지 행위**
- ❌ 계획서/보고서를 읽지 않고 "신규 추가", "강화된" 등으로 표기
- ❌ 특정 항목이 "있을 것 같아서" 마치 있는 것처럼 작성
- ❌ 기억 또는 일반적 상식을 기반으로 비교 내용 생성

**필수 절차**

1. **양쪽 원본 모두 읽기**
   - 계획서 전체 읽기 (Read 도구)
   - 최종 보고서 전체 읽기 (Read 도구)
   - 같은 프로젝트인지 확인 (프로젝트명, 개발기간, FP 등)

2. **실제 차이점만 기록**
   - "계획서에는 X가 없고, 보고서에는 Y가 있다" 형태로만 작성
   - 각 항목마다 출처 명시 (페이지/섹션)
   - 불확실한 항목은 "미확인" 표기

3. **거짓 항목 즉시 제거**
   - 원본에서 찾을 수 없는 항목 발견 시 삭제
   - "신규 추가"라고 표기했던 항목이 실제로는 없으면 수정/삭제

### 예시: 정확한 비교

```
❌ 거짓 (환각):
"최종 보고서에는 '사용자 만족도 4.5/5.0'이 신규 추가되었습니다."
→ 계획서를 읽지 않고 작성 (계획서에는 만족도 항목 자체가 없음)

✅ 정확함:
"계획서 p.1에는 없고, 최종 보고서 p.690(5.4절)에만 
'사용자 만족도 4.5/5.0, 교육참석 15명 100%' 항목이 있습니다."
→ 양쪽 모두 읽고 검증한 후 작성
```

## 2️⃣ 검증 프로세스 (비교/영향도/분석 작업 시)

### 단계별 체크리스트

#### 📋 Step 1: 사전 검증 (작업 시작 전)
- [ ] 요청이 "비교", "분석", "영향도" 등의 키워드를 포함하는가?
- [ ] 필요한 원본 문서가 존재하는가? (없으면 사용자에게 확인)
- [ ] 문서 규모가 너무 크지는 않은가? (너무 크면 Read 도구의 limit/offset 사용)

#### 📋 Step 2: 원본 읽기 (Read 도구 필수)
```
계획서/기존문서 읽기 → 최종문서/현행문서 읽기 → 구조/내용 파악
```

- [ ] 두 문서의 구조를 파악했는가?
- [ ] 섹션/항목 대응 관계를 파악했는가?
- [ ] 불일치하는 부분을 찾았는가?

#### 📋 Step 3: 실제 차이점만 추출
```
계획서 항목 ←→ 최종 보고서에서 찾기 ← YES or NO?
```

- [ ] "신규 추가" 항목들이 정말 계획서에 없는가?
- [ ] "강화된" 항목들이 정말 더 상세해졌는가?
- [ ] "생성된" 항목들이 실제로 존재하는가?

#### 📋 Step 4: 거짓 항목 삭제
- [ ] 원본에서 찾을 수 없는 항목은 모두 삭제했는가?
- [ ] 불확실한 항목은 "미확인" 표기했는가?

## 3️⃣ 거짓 정보 감지 및 제거

### 의심 표현 리스트

| 표현 | 검증 필요 | 확인 사항 |
|------|---------|---------|
| "신규 추가" | ⚠️ 높음 | 계획서에 정말 없는가? |
| "완전히 새로운" | ⚠️ 높음 | 계획서 전체를 읽었는가? |
| "강화된" | ⚠️ 중간 | 양쪽 문서의 해당 섹션을 비교했는가? |
| "처음 도입" | ⚠️ 높음 | 계획서에는 언급되지 않았는가? |
| "~에만 있음" | ⚠️ 높음 | 반대쪽에 정말 없는가? |
| "X개 추가" | ⚠️ 높음 | 개별 항목을 하나씩 확인했는가? |

### 일반적 환각 패턴

#### 패턴 1: 가정으로 작성
```
❌ "일반적으로 보고서에는 성능지표가 포함됩니다."
   → 이 보고서에 정말 있는가?

✅ "이 보고서의 5.3절에 성능지표가 있습니다."
   → 실제로 읽고 확인함
```

#### 패턴 2: 기억에만 의존
```
❌ "앞서 본 계획서에는 사용자 만족도가 없었던 것 같습니다."
   → 확실하지 않으면 말하지 말 것

✅ "계획서 p.1~4를 읽었을 때 사용자 만족도 항목이 없습니다."
   → 실제 읽은 결과만 작성
```

#### 패턴 3: 부분만 읽고 전체인 척
```
❌ "보고서에 ROI 분석이 없습니다."
   (사실: 마지막 섹션에 있는데 못 읽음)

✅ "보고서 p.1~500을 읽었는데 ROI 분석이 없습니다."
   → 범위를 명시하면 검증 가능
```

## 4️⃣ 작업별 체크리스트

### 비교분석 보고서 작성 시

```
□ 계획서 전체를 Read 도구로 읽었는가?
□ 최종 보고서 전체를 Read 도구로 읽었는가?
□ 두 문서가 같은 프로젝트인지 확인했는가?
□ 섹션별 대응 관계를 표로 정리했는가?
□ "신규 추가" 표기한 항목을 계획서에서 찾아봤는가?
□ 찾을 수 없는 항목은 삭제했는가?
□ 불확실한 항목은 "미확인" 또는 "검증 필요" 표기했는가?
□ 각 항목마다 출처(페이지/섹션)를 명시했는가?
□ 최종 검수: 문서 다시 한번 읽어서 거짓 정보가 없는가?
```

### 영향도 분석 작성 시

```
□ 수정 대상 파일을 직접 읽었는가?
□ 참조하는 파일들을 모두 Grep/Read로 확인했는가?
□ "영향을 줄 수 있다"고 표기한 파일들을 실제로 검사했는가?
□ 추측이 아닌 실제 코드 기반으로만 작성했는가?
```

### 기능 설명/현황 분석 시

```
□ 실제 코드/문서를 읽었는가?
□ 스크린샷이나 메모리만 믿지 않았는가?
□ "~하는 것 같다"는 추측을 피했는가?
□ 불확실한 부분은 사용자에게 확인했는가?
```

## 5️⃣ 기존 문서 검증 (문서 드리프트)

> 앞의 1️⃣~4️⃣가 **Claude가 새로 쓰는 내용**의 환각을 막는 규칙이라면, 이 절은 **이미 작성되어 있는 문서가 현재 소스와 어긋난 상태**를 검출하는 규칙이다.

### 원칙

**기존 문서에 적혀 있다는 사실은 그것이 사실이라는 근거가 아니다.**
문서는 작성 시점에는 맞았더라도 이후 코드 변경으로 어긋난다. 기존 문서를 수정·인용·승계할 때는 **해당 기술 내용을 실제 소스와 대조**한다.

### 대조 대상

| 문서가 기술한 것 | 대조할 원본 |
|----------------|-----------|
| 화면 구성, 탭·버튼·영역 | `templates/*.html` |
| 메뉴 경로, URL | 라우트 정의 (`routes/`) |
| 필드명, 테이블명 | DDL, 모델 정의 |
| 조작 절차 ("○○ 탭 선택") | 해당 UI 요소의 실존 여부 |
| 기능 목록, 건수 | 실제 엔드포인트 전수 |

### 실제 사례

```
문서 기재:  관리자 설정 화면은 탭 6개
            (설정 / 사용자 / 데이터 권한 / 상태 코드 / 아이콘 / API 관리)

소스 확인:  templates/mngr_sett.html 의 data-tab 속성 → 탭 11개
            "상태 코드" 탭 없음 · "API 관리" 탭 없음
            (API 키 관리는 /api_key_mngr 별도 메뉴)

결과:       "상태 코드 탭 선택" 절차를 운영자가 수행할 수 없음
```

문서를 그대로 믿었다면 **실행 불가능한 운영 절차**가 그대로 남았을 것이다.

### 필수 절차

1. 문서가 기술한 UI/기능을 **원본에서 직접 확인**한다 (Grep/Read)
2. 불일치 발견 시 **작업을 멈추고 사용자에게 보고**한다
3. 서식·규격 작업 중 발견한 내용 오류는 **임의로 재구성하지 않는다**
   → 정정 표기만 남기고 처리 방향을 확인한다 ([01.legacy-protection.md](01.legacy-protection.md) 🟡 승인 필요)
4. 캡처 이미지로 교차 검증이 가능하면 **이미지를 직접 열어** 확인한다
   → 파일명만 보고 내용을 단정하지 않는다

## 6️⃣ 위반 시 처리

### 환각 발견 즉시 조치

1. **작업 중단**
   - 현재 진행 중인 작업 멈춤

2. **원인 분석**
   - 어디서 환각이 발생했는가?
   - 왜 검증을 건너뛰었는가?

3. **수정 및 재작성**
   - 거짓 정보 삭제
   - 원본을 다시 읽어서 정확한 내용으로 재작성
   - 사용자에게 수정 사항 보고

4. **예방**
   - 이전 환각과 유사한 패턴 앞으로 주의

### 사용자 지적 시

- ✅ 즉시 인정 ("제가 환각으로 작성했습니다")
- ✅ 원본 다시 읽기
- ✅ 거짓 항목 제거
- ✅ 정확한 버전 재작성
- ✅ 같은 실수 반복 방지

## 예외 상황

### "완전한 검증이 불가능한 경우"

**상황**: 문서가 너무 크거나, 일부 섹션만 요청받은 경우

**처리**
```
1. 사용자에게 제약 사항 알리기
   "보고서 전체를 읽을 수 없어서, 제공하신 부분만 분석합니다."

2. 검증 범위 명시
   "p.1~100까지만 읽었으므로, 그 이후 섹션에는 관련 내용이 있을 수 있습니다."

3. 확실하지 않은 항목 표기
   "미확인" 또는 "검증 필요" 표기

4. 사용자 확인 요청
   "전체 문서를 봐야 정확한 분석이 가능한데, 검토해주실 수 있을까요?"
```

## 체크: 이 규칙이 언제 적용되는가?

✅ **반드시 적용**
- 계획서 vs 보고서 비교
- 영향도/가능성 분석
- 현황/상태 정리
- "~가 있나요?" 형태의 검색 요청

✅ **권장 적용**
- 기능 설명 (실제 코드/UI와 비교)
- 성능/品質 분석
- 리스크/개선사항 정리

❌ **적용 불필요**
- 사용자가 제공한 정보 재정리 (그 정보를 있는 그대로 사용)
- 순수 코드 작성 요청 (새로 만드는 코드)

## 참고: Legacy Protection과의 관계

| 규칙 | 초점 | 대상 |
|------|------|------|
| **Hallucination Prevention** | "거짓 정보 생성 방지" | Claude의 환각 행위 |
| **Legacy Protection** | "무단 수정 방지" | 기존 코드/파일 |

> 두 규칙은 상호 보완적입니다. Hallucination Prevention이 "거짓을 말하지 말 것"이라면, Legacy Protection은 "검증 없이 건드리지 말 것"입니다.
